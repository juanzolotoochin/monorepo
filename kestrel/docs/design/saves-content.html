Data · open decisions

Saves, content and IDs

The game reads authored files (items, units, recipes, maps) and writes runtime state (saves, input logs). In lockstep every peer must load exactly the same rules, and a save is also what a joining player receives. This page covers how that data is split, named and stored.

The shape of it

Four kinds of data, one loading path

The key simplification: a new game is just a save at tick 0. The host turns a scenario into a tick-0 save, and from then on, starting, loading, joining, resyncing and re-hosting all go through the same "load a save" code.

AuthoredContentItem, unit, building and recipe definitions. Ships with the game. Same on every peer.
AuthoredScenarioA starting setup: world generator seed and settings, hand-placed buildings, waves. The successor to today's level .ron files.
RuntimeSaveFull simulation state at one tick. Used to load, join, resync and re-host.
RuntimeInput logTurns since a save. Save plus log replays exactly. Used by demos, tests and desync debugging.

A side effect: world generation only runs on the host, and everyone else receives the result as a save. So the generator itself doesn't need to be cross-platform deterministic for multiplayer. It's still worth making it deterministic for tests and replays.

Decision 1

Separating gameplay data from visual data

Today one scenario entry mixes rules (capacity, speed, every) with presentation (skin, label, stock_layout, cargo_anchor). In lockstep, peers must refuse to play together if their rules differ, so we hash the rules. If visuals are part of that hash, nudging a cargo anchor breaks multiplayer between two builds that play identically.

Option A · recommended

One file per definition, with sim and view sections

  • Everything about the ox stays in one place for whoever edits it
  • The loader gives the simulation only the sim section, so the simulation crate can't depend on visual fields
  • Only sim sections feed the rules hash
  • The schema has two halves to keep in mind
Option B

Separate files for rules and visuals

  • Strictest separation; could live in different folders or be owned by different people
  • Two files to keep in sync per definition, joined by string ID
  • Easy to add a unit and forget its visuals, or the reverse
Option C

Mixed, as today

  • No change to authoring
  • Every visual tweak forces every player onto the exact same build
  • The simulation has to carry fields it never uses

Numbers in content are written as decimals (speed: 1.5) and converted to Fx once at load. Decimal parsing is exact on every platform, so every peer gets the same bits. Authors never see fixed-point.

Decision 2

Content IDs: names in files, numbers at runtime

Files name things with strings like "iron". The simulation should use small numbers, an index into the item table, so that stock is an array indexed by item instead of a BTreeMap<String, u32> as today. The question is what a save stores, because indices shift when content is added.

Scenario: a save was written with build 1. Build 2 adds "copper", which sorts before "iron". Then the old save is loaded.

Option A

Raw indices only

  • Smallest saves, nothing to remap
  • Any content change silently turns iron into copper in old saves
Option B · recommended

Indices plus the save's own name table

  • Runtime is dense indices everywhere
  • The save header lists index → name as it was when written. Loading remaps old indices to the current ones.
  • A name that no longer exists gives a clear error, for example "save uses item 'tin', which was removed"
  • A small remap pass at load
Option C

Strings everywhere

  • Saves are self-describing
  • String keys in hot simulation data, which is slow and large at 100k entities

Entity IDs (generational, assigned in apply) and player IDs are separate from content IDs. Player IDs are stable across sessions: a local profile ID now, Steam or EOS ID later. They let a re-hosted save give each returning player their own avatar back.

Decision 3

What a save file looks like

A save has three jobs. It must be byte-identical on every peer at the same tick, so peers can compare hashes and skip the download when joining. It must be small and fast, because joining players wait for it. And it must be readable when something goes wrong, because desync dumps are diffs of saves.

Rough numbers: terrain is 512 × 512 × 32 voxels at 1 byte each, and mostly uniform rock compresses very well. At 2–5 MB, a join over a typical home connection takes a few seconds, and over LAN it is instant.

Option A · recommended

Sectioned binary, plus a text view for debugging

  • A header (format version, game version, rules hash, name tables, tick) followed by one section per subsystem and per terrain chunk
  • Each section uses serde derives encoded with postcard and compressed with zstd
  • The same serde types can print as RON text, which gives readable dumps and diffs for free
  • Sections line up with the per-chunk hashes, so a joiner can skip the chunks that already match
  • The container format is ours to write, though it is small
Option B

One serde blob

  • One line to save, one line to load
  • All or nothing: no partial transfer, no per-section versions
  • A dump is one huge diff
Option C

Text saves (RON or JSON)

  • Human-readable everywhere
  • Several times larger and slower; tens of MB for terrain
  • Float-looking text for Fx values invites mistakes
Decision 4

Old saves after the game changes

While the architecture is young, the save layout will change every week. Keeping old saves loadable means writing a migration for every change. Multiplayer already requires the exact same build, so compatibility matters only for single-player or re-hosting old worlds.

Option A · recommended

Refuse mismatches for now

  • No migration code while things move fast
  • Saves state their format version, and loading an old one gives a clear message, not a crash or corrupt world
  • Name tables (decision 2) already handle the most common change: added content
  • Long test worlds are lost when the format changes
Option B

Migrations from day 1

  • Worlds survive every update
  • Every field rename needs a migration and a test
  • Slows down exactly the phase where the design is still changing

The usual turning point is when other people start keeping worlds they care about, such as an early-access release. Per-section versions make it possible to add migrations then, one section at a time.

Your call

The four questions

  1. Content split. One file per definition with sim and view sections (recommended), separate files, or mixed as today.
  2. Content IDs. Dense indices with a name table in each save (recommended), raw indices, or strings.
  3. Save format. Sectioned binary with a RON debug view (recommended), one serde blob, or text.
  4. Compatibility. Refuse mismatched saves for now (recommended), or migrations from day 1.

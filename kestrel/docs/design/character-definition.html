Kestrel / design discussion / 25 October 2026

A character is assembled from five sources.
It should be one definition.

No type in the code says "this is a character". Gameplay stats, abilities, visuals, animation and behaviour each live in their own place and are joined by string ids and by which scene is loaded. This page proposes a single CharacterDef and lists the decisions needed before building it.

Scope: kestrel/sim, kestrel/content, kestrel/app and tools/assetc. The full source survey, with file references, is character-architecture.md. This is a design proposal. Nothing beyond the quick fixes below has been implemented.

Where a character comes from today

Stats · NPCsScenario RONlevels/*_supply.ron: agent speed, radius, capacity; wave hp, armor, damage.
Stats · playerRust constantssim/…/avatar.rs: walk/run speed, acceleration, body radius, swing and jump timings.
AbilitiesScene flagsJump, SwiftSword, Digging in the layout RON. They belong to the scene, not the character.
VisualsStyle RONstyles/*.ron: actor meshes, skins, materials, character_motion, including walk and run speed.
AnimationTwo rig systemsThe player uses character.rs Pose. Everything else uses rig.rs Rig::pose.
Consequence: a character's identity is a property of the scene. Each scene has exactly one player look. The forest ghoul and the combat-arena ghoul are two separately authored skins that have already drifted apart.

Players and AI share no action vocabulary. Players send CommandKind and Intent. Haulers send economy messages. Only players strike, and threats never attack agents.

Findings

Fixed on this branch

Duplicated avatar rules between sim and view

Swing timings, the combo window, hover height, and the prediction's acceleration and radius now come from sim::settlement::avatar. SwordStroke::combo is the single combo rule. A test pins the style default speeds to the sim's. Memory-trial commands now check ownership, so a guest can no longer teleport the host. Golden hashes are unchanged.

Open · gameplay change

The player has two radii

The avatar collides at BODY_RADIUS 0.32, but haulers steer around it at the scenario radius 0.18. Unifying them changes hauler paths and needs a golden update.

sim/src/settlement/haulers.rs:281, avatar.rs:27, mod.rs:516

High · rules hash

Gameplay speed travels through a visual file

A style's character_motion.walk_speed and run_speed become the sim's locomotion when they differ from the defaults. Style files are not in the rules hash, so peers with different styles could desync without a warning.

app/src/lockstep.rs:380–388

Medium · maintenance

Player posing is written three times, over two rig systems

The local player, remote players and Character Studio each build their own Pose. Rig pivots (0.94, 0.58, 1.49 …) are repeated in rig.rs, scene.rs and viewer.rs. Studio infers what a character can do from mesh coverage.

character.rs:317, peers.rs:109, viewer.rs:900–1020, character_catalog.rs

Medium · structure

One struct for two roles, separate tables for a third

AgentState holds hauler fields (links, assignment, trailer, phase) next to avatar fields (avatar, attack_ready), and every avatar method re-checks controlled. Cargo is modelled three ways. Threats are a different struct with hard-coded radii that ignore the skin's scale.

Already right

What to build on

content already has the target shape: one RON file per definition, with a sim section that feeds the rules hash and a view section that doesn't. Movers use it today. Rig, with motion chosen from asset metadata, already poses every non-player entity. The sim/view state boundary holds.

Proposal: CharacterDef

One file per character under content/data/character/, loaded like movers. The sim section is rules-hashed and fixed-point. The view section is free to change between peers.

// content/data/character/ghoul.ron
(
  sim: (
    body:      (radius: 0.27),
    move:      (walk: 1.6, run: 1.6, accel: 26, brake: 32),
    health:    (hp: 3, armor: 0),
    brain:     FollowRoute,          // Player | Hauler | FollowRoute | Turret
    abilities: [],                   // Jump, Dig, Jetpack, Weapon(Sword, swift: true) …
  ),
  view: (
    skin: "ghoul", rig: Biped, scale: 0.52,
    motion: (step_distance: 0.5),
    sounds: (hit: GhoulHit),
  ),
)
AreaChange
ScenariosPlace characters by id: agents: [(character: "worker", position, links)], waves: [(character: "ghoul", count, every)]. Stats stop being repeated per scenario.
ScenesName the player character, for example player: "exosuit", instead of carrying ability flags.
StylesBecome mesh and material libraries only. No gameplay values pass through them.
Sim storageKeep per-role SoA tables for the 100k-entity budget. Each entity stores a CharacterIx into Rules. Avatars, haulers and threats share one body struct (position, heading, velocity, radius, health).
ViewThe exosuit becomes an actor recipe. One rig path, and one function that builds a pose from mirror state for the local player, peers and Studio.
BrainsA shared intent or action vocabulary (move, go to, attack, interact) that player commands and AI both produce.

Migration, each step shippable on its own

  1. Sim stats only. Add CharacterDef to content. Point the player constants and wave stats at it. No behaviour change.
  2. Scenarios reference characters. Agents and waves name a character id. Scenario files lose duplicated stats.
  3. Abilities move to characters. Jump, dig, jetpack and swift sword stop being scene flags. Styles stop feeding locomotion into the sim.
  4. View section and one rig. The exosuit becomes a recipe, posing is shared, and Studio reads capabilities from the definition.
  5. Shared brain seam. A common action vocabulary for players and AI. Threats become characters with a brain.
Determinism check for step 1: RON decimals are parsed into Fx. A parsed 3.8 may not have the same bits as today's hand-written from_bits constant. Either assert bit-equality during the move, or accept one golden update.

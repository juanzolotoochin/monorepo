Simulation core · open decisions

Big entities

A giant spider with a 4 × 4 tile body can straddle a chunk border, block corridors smaller units fit through, and shove smaller units aside. The ownership rule from the message system handles part of this. Three things still need decisions.

Already settled

One owner, no copies

The spider belongs to exactly one chunk: the one containing its center. Only that chunk updates it and writes its messages, so it can never be processed twice or end up in two outboxes. Its body can overlap up to four chunks, but that only matters to other entities looking for it.

Reading never depends on sleep. A sleeping chunk is skipped for updates, but its entities can still be read by queries from awake neighbors.

Decision 1

How other entities find a big entity

A tower searches the chunks its range circle touches. If it only looks for entities owned by those chunks, it can miss a spider whose body is in range while its center sits in a chunk the circle doesn't reach. Switch between the three approaches.

Zoomed in on the corner where four chunks meet. Each grid square is one tile. Real chunks are 32 tiles wide; this view shows 12 tiles of each.

Option A

Owner only

  • Nothing extra to build
  • Misses big entities whose center is just outside the searched chunks
  • Towers ignore a spider that is visibly inside their range
Option B · recommended

Widen the search by the largest radius

  • One line: search radius = range + largest body radius
  • Nothing to keep up to date as entities move
  • A 4 × 4 body has a radius of about 2.8 tiles, small next to 32-tile chunks
  • Needs a size cap; a 40-tile boss would widen every search
Option C

Register in every overlapped chunk

  • Exact; works for any size, even bigger than a chunk
  • Each chunk keeps a list of foreign bodies, rebuilt in housekeeping whenever they move
  • Every query must remove duplicates

Option B with a size cap of 8 tiles, and Option C added later only for "huge" bosses above the cap if the game ever has them. Every search ends with an exact footprint test, so widening never causes false hits. It only adds candidates to check.

Decision 2

Paths for different body sizes

A corridor 3 tiles wide is open to a 1 × 1 enemy and a 2 × 2 hauler but closed to the spider. Pathfinding has to know that. The usual tool is a clearance map: for each tile, the largest square body whose top-left corner can stand there. It is computed once per chunk and recomputed only when the terrain changes there.

Wall or dug-out rock Body fits with its corner here Too tight

The number on each tile is its clearance. A body of size N can use a tile whose clearance is N or more.

Option A · recommended

A few size classes

  • Sizes 1, 2 and 4: one flow field per target per class instead of one per entity
  • Hundreds of spiders share one size-4 field
  • Hauler A* (already clearance-aware in the current code) just reads a different threshold
  • Body sizes snap to a class, so a 3 × 3 creature paths as a 4
Option B

Any size, per entity

  • Exact for every body
  • Flow fields can no longer be shared across sizes, so enemy pathing cost grows with the number of distinct sizes
  • Hard to budget at 100k entities
Decision 3

When bodies bump into each other

Big entities make unit-to-unit collision visible: a spider walking through a crowd of small enemies should push them aside, not pass through them. That collides with the core rule. During the parallel self update, an entity may only write itself, but steering around others means reading their positions while they are being written.

The fix is to read last tick's positions. Before self update, positions are copied into a read-only snapshot. Every unit steers from the snapshot and writes only its own new position. No thread ever reads a value another thread is writing.

Self update with soft separation

// before stage 2, once per tick prev_pos.copy_from_slice(&pos); // read-only snapshot // stage 2, parallel per chunk, entities in ID order for e in chunk.units() { let push = separation(e, &prev_pos, neighbors); // reads others' old positions vel[e] = steer(flow_field_dir(e), push); // writes only itself pos[e] += vel[e] * DT; }

Heavier bodies push harder: the push is scaled by mass ratio, so the spider barely slows while small enemies slide away. It's soft, so units can overlap a little in a crush. That keeps it cheap and stable.

The snapshot rule applies beyond collision. Anything in self update that needs to read another entity reads last tick's copy. That rule keeps the parallel stage deterministic.

Context · no decision needed

Big buildings

Buildings don't move, so they are simpler. A 3 × 3 smelter is owned by the chunk of its anchor tile and also marks its tiles in the terrain occupancy grid, which may span two chunks. Placing it is a message. Apply checks every tile is free, marks them, and makes those chunks' clearance maps and navigation dirty. Apply runs on one thread, so writing tiles in two chunks is safe.

Your call

The three questions

  1. Finding big entities. Widen searches by the largest body radius with a size cap (recommended), register in every overlapped chunk, or owner only.
  2. Paths by size. A few size classes with shared flow fields (recommended), or exact size per entity.
  3. Unit collision. Soft separation from last tick's positions (recommended), no collision, or hard collision.

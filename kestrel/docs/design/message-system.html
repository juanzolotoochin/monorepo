Simulation core · open decisions

The tick message system

How one simulation tick runs so that it can use many threads and still produce exactly the same result on every machine. Three decisions are open: the mutation rule, how messages are queued, and who wins when two messages conflict.

The problem

Threads finish in random order

With 100k entities we want every core working. But if two threads both change the same depot, the result depends on which thread got there first, and that differs between machines and between runs. One different number and the peers desync.

The fix is to split each tick into a parallel phase that never writes shared state and a single-threaded phase that applies changes in a fixed order.

One tick, six stages

Green stages run in parallel across chunks. Amber stages run on one thread. In the stepper below, the stage of the current step is highlighted.

Decision 1 · the core rule

An entity may change itself directly in a parallel loop. Anything that touches another entity or a shared resource must be a message.

Self-changes (direct, parallel)

  • Moving along a path
  • Projectile flight
  • Cooldowns and timers
  • Animation phase and facing

These are the hot paths: tight loops over arrays with no allocation. Each entity writes only its own memory, so thread order can't change the result.

Interactions (messages)

  • Damage to another entity
  • Reserving, taking or depositing stock
  • Placing or removing buildings
  • Digging a voxel
  • Spawning and despawning

These are rare compared with movement. They are validated when applied, so a message can be rejected if the world changed first.

Why it is deterministic

Per-chunk outboxes

During the read phase each chunk writes messages into its own outbox, iterating its entities in ID order. Threads can finish chunks in any order. The merge always concatenates outboxes in chunk order, so the merged list is identical.

This gives an automatic test: run the same input log with 1 thread and with 16 threads. The state hash must match on every tick.

Decision 2

How messages are queued

Messages of different kinds (reserve, damage, dig, despawn) have to be applied in some order. The question is whether that order comes from one mixed list or from an explicit order of message types.

Option A

One mixed stream

  • One global order, simple to explain
  • A new message type needs no ordering decision
  • The order of kinds depends on where things are on the map
  • One big enum; small messages pay for the largest one
  • Apply code jumps between kinds, so cache use is worse
Option B · recommended

A queue per type, fixed type order

  • The type order is an explicit rule you choose, for example that damage resolves before pickups
  • Each queue is a tight array of one struct
  • Easy to profile and debug per message type
  • The type order is one more thing to maintain
  • A new message type needs a place in that order
Decision 3

Who wins a conflict

When two messages want the same thing, such as the last 4 iron, the earlier one in the order wins and the other is rejected. If chunk order never changes, the entity in the lower-numbered chunk always wins. Players would notice that one side of the base always gets served first.

The demo shows hauler A in chunk 2 and hauler B in chunk 7, out of 16 chunks, competing on every one of 32 ticks.

Player actions are a separate case. They are applied in stage 1, before any AI messages, so a player always beats an AI hauler to the same stock regardless of this choice.

Context · what a chunk is

A chunk is a square of the map

A chunk is a fixed 32 × 32 tile square of the world, covering the full height. The MVP world is 512 × 512 tiles and 32 voxels deep, which makes a 16 × 16 grid of 256 chunks. Chunk (3,7) covers tiles x 96–127, y 224–255.

It is the same square the terrain is already split into for voxel storage and meshing. The simulation reuses it as the unit for nearly everything, so one concept does several jobs.

The MVP world, chunk by chunk

What the chunk is used for

JobWhat it means
MembershipEvery entity belongs to exactly one chunk, the one containing its position. A building that spans a border belongs to the chunk of its anchor tile.
Parallel workStages 2 and 3 hand out chunks to threads. 256 chunks keep 16 cores busy.
OrderingEach chunk iterates its entities by ID and writes its own outbox. The merge order is the chunk order.
SleepingA chunk with no awake entities is skipped by every stage.
Spatial queriesA tower with range 10 only looks at entities in its own chunk and the neighbors its range reaches.
HashingEach chunk has its own hash, which is how a desync gets pinned to "chunk (3,7)".
Terrain and navigationDigging marks the chunk's voxels and walkable spans dirty, and only that chunk is rebuilt.

Crossing a border

A hauler walking from chunk (3,7) into (4,7) moves during self update, but its membership doesn't change mid-tick. In housekeeping (stage 6), entities whose position left their chunk are moved to the new chunk's lists. So during the parallel stages, which chunk owns what never changes.

Hotspots

When 5,000 enemies pile up at one gate, one chunk holds most of the work and one thread does it while the others wait. The fix, when we need it, is to split a heavy chunk into sub-batches by ID range, each with its own outbox, merged in order. Ordering stays deterministic. We can add this later without changing anything else.

Context · no decision needed

Sleeping

Skipping work is the biggest performance win. Most entities are idle most of the time: a full depot, a miner between cycles, a hauler with no job. Sleep and wake must themselves be deterministic, so they only happen through messages or timers, and the sleep flag is part of the save and the hash.

Ways to sleep

  • Chunk sleep: a chunk with no awake entities is skipped in every stage.
  • Wake by message: an idle hauler sleeps until a depot gains stock and sends WakeHaulersNear.
  • Wake by timer: a miner producing every 90 ticks is filed under its next tick and not touched until then.

Timer wheel

Each slot holds the entities to wake on that tick. A tick only looks at its own slot, so 10,000 sleeping miners cost nothing until their slot comes up.

Your call

The open questions

  1. Core rule. Decided: entities change only themselves in parallel loops, and all interactions are messages.
  2. Queues. One queue per message type with a fixed type order (recommended), or one mixed stream.
  3. Conflict order. Fixed chunk order, rotate the starting chunk each tick, or shuffle chunk order each tick with a seed (recommended).

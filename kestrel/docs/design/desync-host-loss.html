Lockstep netcode · open decisions

Desyncs and host loss

Two networking decisions are still open: what happens when a client's simulation stops matching the host, and what happens when the host leaves. Pick a policy on each timeline to see how it plays out tick by tick at 30 Hz.

Decision 1

What happens on a desync

Every peer runs the same simulation from the same inputs, so every peer should hold identical state on every tick. A desync means one peer's state differs from the host's. After that point the peers are effectively playing different games, and the gap only grows.

Detecting it

Each tick, every client hashes its state and sends the hash to the host with its inputs. The host compares it with its own hash for that tick. The hash arrives about one round trip later, so detection lags the divergence by a couple of ticks.

Hashing 100k entities is about 6 MB of state and roughly 1 ms per tick with a fast hash. If needed we can hash every Nth tick or keep the hash incremental.

Localizing it

A single hash only tells you that something differs. We keep separate hashes per subsystem and per chunk, so a mismatch names where to look:

Debugging it

  1. Both sides write a state dump for the bad tick: full state as readable text, plus the input log since the last save.
  2. A diff tool shows the first field that differs, for example depot "smelter_in".items["iron"]: 12 vs 11.
  3. Because the input log replays exactly, you can re-run either side locally in a debugger and stop on that tick.

Usual causes

  • Iterating a HashMap or HashSet
  • A stray f32 or platform math function in the simulation
  • Reading wall-clock time
  • Stale data left in a reused slot
  • Simulation code reading something from the Bevy view

Most of these are blocked by design. The rest is what the dumps are for.

What players experience

Decision 2

What happens when the host leaves

Every peer holds the full game state, so the world itself survives the host leaving. What disappears is the role the host plays for everyone else.

Only the host has

  • Turn authority: decides which inputs run on which tick
  • Hash referee: compares everyone's hashes
  • Join server: sends the save to joining players
  • The platform lobby, later on (Steam or EOS)

Every peer has

  • The complete simulation state
  • All confirmed turns up to its current tick
  • The input log since the last save
  • Everything needed to write an identical save

What players experience

How migration works

  1. Clients stop receiving turns. After a timeout of about 3 seconds, they declare the host gone.
  2. The remaining peers agree on the last confirmed tick: the highest tick every one of them has.
  3. A new host is picked by a fixed rule, such as the lowest player ID.
  4. Everyone reconnects to the new host. Inputs that were sent but never confirmed are dropped and re-entered.
  5. Turns resume from the agreed tick.

What makes it hard

  • Two peers both believing they are the new host, for example after a network split
  • A client that is missing the last turn the others have
  • A packet from the old host arriving after the switch
  • Moving the Steam or EOS lobby ownership along with it

What "design for migration" costs today

We don't build migration yet. We just avoid code that would make it impossible later:

  • The host is a role: an authority: PeerId field in the protocol, not an assumption that peer 0 is in charge.
  • Turn authority is its own module, separate from the host player's simulation and input.
  • Packets carry a session epoch number, so packets from an old host can be ignored.
  • Every peer keeps the last few confirmed turns, not just the host.

That is a few fields and one module boundary, with no extra features to test.

Your call

The two questions

  1. Desync policy. Halt in dev and resync in release (recommended), always resync, or disconnect the desynced client.
  2. Host leaving. The session ends but the code is designed for migration (recommended), the session ends with no migration plans, or we build migration early.

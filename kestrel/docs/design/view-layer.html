View layer · open decisions

The Bevy view layer

The simulation ticks 60 times a second in fixed-point, on data Bevy never touches. The screen refreshes 60 to 144 times a second in f32. This page covers how one becomes the other: smooth motion, instant feedback despite input delay, effects and sound, and where the simulation runs.

Settled by earlier decisions

Data flows one way

Bevy reads input, turns it into commands, and draws what the simulation says. Nothing in Bevy ever writes simulation state. Today's game breaks this rule: the player's walking is done in Bevy and its pose is pushed into the simulation each frame (set_controlled_pose). In the new design, walking is a command and the simulation moves the avatar.

Bevy inputkeys, mouse, f32 cursor
→
Commandquantized to Fx or tile, tagged with tick t+D
→
Simulationturns from host, ticks at 60 Hz
→
Viewrender state + events, drawn by Bevy

After each tick, the simulation produces a render extract: positions, headings, animation states and health of entities in visible chunks, converted to f32, plus that tick's events. Bevy only ever sees the extract.

Matching entities

The view keeps a map from simulation ID to Bevy entity. Spawns, despawns and state changes arrive as events. Continuous values like positions are copied from the extract each frame, only for visible chunks.

The view may be non-deterministic

The view can use HashMap, f32, random particle seeds and wall-clock time. It can skip effects off screen. None of it can affect the game, because nothing flows back except commands.

Decision 1

Smooth motion between ticks

At 60 Hz, positions only change every 17 ms. Drawn directly, units visibly step on a 144 Hz screen, and judder even on a 60 Hz one whenever the screen's clock and the simulation's drift apart. The view needs to invent positions between ticks. It can blend between the last two ticks, or guess ahead from the last one.

What the screen draws Latest simulation tick Path

Slowed down 12×, so it looks like 5 ticks a second. At real speed the differences are smaller but still visible as stutter or jitter.

Option A

Draw ticks directly

  • No lag, nothing to build
  • Motion steps every 17 ms. It looks like a 60 fps game on any monitor, and judders when frames and ticks drift.
Option B · recommended

Interpolate

  • Always smooth, and always shows a position the simulation actually had
  • Simple: keep the previous and current extract and blend
  • Everything is shown one tick (17 ms) late
  • Spawns and teleports must be flagged so they don't slide in
Option C

Extrapolate

  • No added lag
  • Overshoots on every turn and stop, then snaps back
  • Projectiles can visibly pass through their target
Decision 2

Instant feedback despite input delay

With an input delay of 8 ticks (133 ms), a click on tick 100 only takes effect on tick 108, and interpolation shows it a tick later. That's about 150 ms, which feels sluggish for walking and casting. Visual-only prediction shows the start of the action right away, then lets the confirmed simulation take over. The prediction never touches the simulation.

Option A

No prediction

  • Nothing to build, never wrong
  • Every action has about 170 ms of visible delay online, and about 70 ms on LAN
Option B · recommended

Cosmetic feedback, plus a predicted own avatar

  • Casts, ghosts and UI respond instantly with no simulation involved
  • Your avatar runs the same Fx movement code on a private copy: last confirmed position plus your unconfirmed inputs
  • When the confirmed position differs, for example because the spider shoved you, the view eases toward it
  • The movement code must be callable on a single entity outside the tick
Option C

Cosmetic feedback only

  • Simpler: the avatar just leans or starts its walk animation toward the input
  • Your own walking still feels delayed, and walking is the most frequent action

Option B's avatar prediction is a tiny rollback for one entity. It replays a few ticks of your own movement against the confirmed world, in the view, every frame. It's cheap because it's one entity, and safe because the result is only drawn.

Decision 3

Where the simulation runs

At 60 fps a frame has 16.7 ms, and a 60 Hz tick happens in every frame. If the tick runs inside the Bevy frame, every frame carries its whole cost. A heavy tick then makes every frame late, and the whole game drops below 60 fps.

Bevy rendering work (6 ms) Simulation tick on the frame's thread 16.7 ms frame budget
Option A · recommended

In the frame first, behind the extract

  • Simplest to build and debug: one thread of control
  • Fine while ticks stay under about 10 ms, and your prototype ran 1M entities in 6 ms
  • Bevy only reads the render extract, so moving the tick to its own thread later doesn't change view code
  • If ticks grow, the frame rate drops and we have to do the move
Option B

Own thread from the start

  • Frame times stay flat regardless of tick cost
  • A stall waiting for network turns never freezes rendering
  • Commands and extracts cross threads through queues and a triple buffer
  • Harder to debug while the basics are still moving
Context · no decision needed

Effects and sound

The apply phase emits events (Fired, Hit, Died, Dug, Delivered) tagged with their tick. The view plays each one when interpolated render time reaches that tick, so the impact sound lands exactly when the projectile is drawn arriving.

  • Events are advisory. The view may drop them (off screen, too many sounds at once), and the simulation never knows.
  • When several ticks run in one frame to catch up, events from all of them are queued and play in order.
  • Dying units are handed to the view: the simulation removes the entity, and the view keeps a corpse for its death animation. Today's game already does this.
  • While the simulation stalls waiting for a turn, render time stops at the latest tick. Units freeze in place rather than sliding past where they really are.
Your call

The three questions

  1. Smoothing. Interpolate between the last two ticks (recommended), extrapolate, or draw ticks directly.
  2. Prediction. Cosmetic feedback plus a predicted own avatar (recommended), cosmetic feedback only, or none.
  3. Simulation thread. In the Bevy frame first, behind the render extract (recommended), or on its own thread from the start.

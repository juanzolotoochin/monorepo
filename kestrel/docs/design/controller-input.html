Kestrel / architecture review / 25 October 2026

Input already has a command boundary.
It needs an action boundary.

Controller support fits the existing deterministic simulation. The missing piece is a shared front-end layer that resolves devices, focus, aiming, and interaction targets before gameplay sends commands.

Scope: the full game in kestrel/app, traced through services, session, networking, and simulation. kestrel/play is a separate minimal test front end. This is a source review and design proposal; runtime behavior and physical controllers have not been tested for this review.

The user selected the baseline and all nine recommended behaviors on 25 October, then specified USB and hardware-free testing first. The consolidated specification is in controller-support.md. The options below remain editable for revisions; they do not need another round of confirmation.

Small typed action/context layer. Windows native first; one controller for the local network player; keyboard/mouse coexistence; fixed bindings; gameplay, main menu, and pause navigation. No local split-screen or browser controller milestone.

First implementation milestone: synthetic controller input. The implementation machine may have no controller. A synthetic source must supply connection, buttons, triggers, and sticks to the same snapshot consumer used by the native source. This exercises bindings, dead zones, claiming, arbitration, contexts, targeting, and command dispatch without virtual-device drivers. Include automated timed scenarios and a developer-only rendered replay path. Physical validation later uses an Xbox-compatible USB controller; exact model is unspecified.

  • Stick direction uses existing walk/run speeds with a separate run action. Proportional analog speed is deferred.
  • Right stick aims independently. Nearby interactables support logistics. Neutral aim retains the last valid direction.
  • Pause, focus loss, or selected-controller disconnect stops direct movement, disables thrust, clears pending local action edges, and cancels click routes. Accepted logistics jobs continue.
  • Device data and floats remain in the front end; fixed-point semantic commands pass through SessionService/Session, authoritative turns, and accepted-turn replay.

Agreed action and context contract

Sample → route → dispatch. Sample physical state once per frame in the App layer. App context handlers resolve text entry, menu, and utility UI before Session pause handling and World gameplay dispatch. An opening or closing UI action is consumed, so it cannot also attack/interact. A focused text field receives text messages separately. Keep context precedence explicit and resolve cancellation before gameplay dispatch.

Edges and held state. Attack, interact, equip, jump, drop, and UI confirm consume one press edge. Run and jetpack use held state; thrust also emits release/cancel. A trigger has separate press/release thresholds so noise cannot create repeated presses. Emit each edge once even if Step catches up multiple ticks. Coalesce only continuous movement/aim changes. Quantize the unit directions and compare against the last sent value before queueing.

Suspension and return. Focus loss and selected-controller disconnect open the pause overlay during a live session. Focus return/reconnect never auto-resumes. Held buttons and non-neutral sticks must return to released/neutral before contributing again. A newly connected controller claims the local seat with a fresh Menu/Start press; that claim press is consumed. Other controllers are ignored. Selected-controller disconnect cancels gameplay and requires a new claim or explicit keyboard/mouse resume.

Cancellation has latency. Clear unsent input edges and the local follow-up attack buffer. Commands already accepted into turns cannot be recalled: an accepted attack or jump finishes normally, and remote thrust/stop takes effect when its turn is applied. The view may respond to suspension immediately, but must reconcile with authoritative state.

Job travel needs special treatment. sim::Settlement::move_avatar unconditionally cancels a pile job, including for Stop; logistics itself uses GoTo travel. Therefore an unconditional walk(0) cannot implement the chosen policy. Selected solution: a semantic release command that disables thrust and stops movement only when an accepted logistics job does not own the route, evaluated on authoritative state. This extends the command vocabulary and needs protocol/replay compatibility checks; it does not move device handling into the simulation. See decision 9.

Evidence: sim/src/settlement/avatar.rs:620–647, 721–742, sim/src/settlement/piles.rs:450–523, 539–546. Agreed behavior is not implemented.

How input reaches the game today

01 · DevicesBevy input stateButtonInput<KeyCode>, mouse buttons, cursor position, scroll. Menu typing also reads KeyboardInput messages.
02 · InterpretationMany independent readersFlow, menus, pause, settlement, piles, memory, PlayerControl, and camera systems interpret hardware directly.
03 · Gameplay requestsPlayerControl + feature helperswalk, go_to, aim, and strike partly centralize avatar commands. Other features queue commands directly.
04 · Command boundarySessionService → SessionCoordinates are quantized to fixed point. Session::queue(CommandKind) selects host, client, or replay behavior.
05 · Authoritative turnHost / client schedulingHost input enters the current open tick. Clients request host tick + estimated one-way latency + input delay. Late client input moves to an open turn.
06 · Simulation + viewApply → simulate → mirror → presentSimulation validates avatar ownership, applies commands in player order, and runs movement/combat. Bevy mirrors confirmed state and previews local movement/attacks.
Preserve this boundary: device data and floating point stay in the front end. The network, replay log, and simulation receive semantic, fixed-point commands such as MoveAvatar, AimAvatar, Attack, and Transfer.

Ordering is part of the current input design

Every frame runs Input → Step → Mirror → Present. Inside a phase, App services run before Session services, then World services; each layer follows registration order. Pause is registered before SessionService, so it can erase keyboard/mouse state before those readers. PlayerControl runs after the other World services; its handlers are chained mouse → attack → keyboard → showcase.

One exception matters: memory recording reads E/Q and queues commands in Phase::Mirror, after that frame's Step. It should move into the shared Input path when input is extracted.

Evidence: app/src/main.rs:228–263, service/src/lib.rs:217–229, 399–418, app/src/lockstep.rs:137–140, 240–245, 712–721, app/src/palimpsest/mod.rs:20–22, 101–123, net/src/host.rs:209–212, net/src/client.rs:164–175.

Response and replay

Walking and aiming are persistent simulation state. PlayerControl sends movement only when its quantized direction/run pair changes, and laser aim only after a direction change of roughly 0.02 in vector distance. Right-click routes are reconsidered at most every 0.12 seconds. Fx::quantize rounds to 1/1024 of a tile before fixed-point normalization. Attacks queue a command and begin local visual feedback immediately.

The host and solo player show the newest confirmed pose. Joined clients use an approximate floating-point movement preview, bounded to 0.9 m ahead, then reconcile with confirmed state. This preview is separate from authoritative movement. Input recordings store accepted turns, not raw keys, buttons, or device identities; replay ignores new queued simulation commands.

Evidence: app/src/lockstep.rs:727–782, 821–905, 1008–1018, fx/src/fx.rs:153–154, session/src/lib.rs:153–160, 271–277.

What needs attention before controller support

High · competing writers

A second movement reader would fight the keyboard

keyboard_input calls walk(0) whenever no keys are down and PlayerControl still has a nonzero walking direction. A gamepad reader that also calls walk would be stopped by the keyboard or overwrite its result, depending on ordering. Mouse, attack, and keyboard already resolve precedence by execution order.

Recommendation: arbitrate device contributions once, then dispatch one movement result. Define keyboard/gamepad takeover, pointer route cancellation, and automation ownership explicitly.

Evidence: lockstep.rs:716–720, 739–748, 984–993.

High · cancellation semantics

Clearing raw input does not release every persistent action

Pause uses reset_all() for keys/mouse and zeroes scroll. Keyboard walking can become a stop on the same frame, but jetpack disable depends on just_released(Space); resetting input does not emit that release. No explicit pause transition disables thrust or cancels an existing GoTo route. The world continues running. Disconnect and focus loss need the same semantic cleanup.

Recommendation: on losing gameplay context, issue deliberate movement/thrust cancellation, clear pending local actions, and require a fresh press for one-shot actions on return. Decide separately whether autonomous routes/jobs should continue.

Evidence: pause.rs:127–141, lockstep.rs:967–975, 991–993, persistent intent in sim/src/settlement/avatar.rs:83–90, 620–647. This is a source-derived risk; no runtime reproduction was performed.

Design constraint · analog movement

Stick magnitude is discarded at the existing helper

PlayerControl::walk normalizes every nonzero vector. A slight tilt and a full tilt therefore become the same walk speed; run is a separate boolean. The documented simulation contract likewise calls for a unit direction. The movement integrator multiplies direction by speed, so proportional input may fit the existing vector shape, but it requires an explicit bounded-magnitude contract and matching preview behavior.

Recommendation: choose directional movement for the smallest first milestone, or deliberately preserve a clamped [0,1] magnitude through quantization and simulation. Add radial dead zone and hysteresis before command generation; exact-vector change detection alone would send stick noise frequently.

Evidence: lockstep.rs:739–748, 851–865, sim/src/settlement/avatar.rs:83–90, 326.

Design constraint · targeting

Buttons are only half of controller support

Attack and laser aim need a Window, Camera, and cursor surface hit. Logistics has separate ray/ground/UI targeting. A right stick naturally supplies a direction, while a depot interaction needs an entity or world point. Mapping a trigger to mouse-left does not supply either target.

Recommendation: represent aim direction and interaction target separately. Allow mouse raycasting, stick aim, and a selected nearby interactable to feed common gameplay helpers. Aim from confirmed gameplay state, as the mouse attack already does.

Evidence: lockstep.rs:1024–1064, piles/mod.rs:259–363, settlement.rs:1129–1176.

Medium · inconsistent action ownership

Feature modules duplicate binding and context rules

E means machine toggle or memory record/deploy. Shift disambiguates interaction and combat. Settlement's manual-movement check covers WASD and right mouse but omits arrow keys, even though movement supports them; transfer-cancellation dispatch therefore differs by binding. Memory input is read during Mirror. These rules would need duplicating for each new device.

Recommendation: make feature availability and action consumption explicit. Put transfer cancellation in the shared manual-movement action path. Keep text entry on a separate text-message path.

Evidence: settlement.rs:1078–1094, lockstep.rs:984–986, 1056–1058, palimpsest/mod.rs:101–123, menu.rs:433–490.

Readiness gap · platform and UI

The repo has no controller handling or controller UI navigation

The Bevy dependency disables defaults and lists explicit features. No gamepad backend is explicitly enabled there, and searches found no Gamepad reader or bevy_gilrs dependency in Kestrel/Cargo.lock. Menus lack shared directional focus/confirm/back actions. Native and browser device discovery must be verified independently against the pinned Bevy version before calling support complete.

Recommendation: include device connection/selection, disconnect cancellation, menu focus, and last-active-device prompts in the controller scope. Confirm the backend/build configuration without changing deterministic crates.

Evidence: Cargo.toml:10, Cargo.lock, menu.rs:372–500, pause.rs:54–73. Backend readiness is based on repository configuration, not a hardware test.

Recommended architecture

Bevy keyboard/mouse   Bevy gamepad   scripted action tests
          \                |                /
          Device adapters + bindings + dead zones
                           ↓
          Context routing / focus / device arbitration
                           ↓
          Semantic actions: Move, Aim, Attack, Interact,
          JumpOrFly, Dig, Equip, Pause, UI navigation
                           ↓
          Target resolution + feature-specific actions
                           ↓
          PlayerControl / shared gameplay command helpers
                           ↓
          SessionService → Session → turns → simulation

Menu focus consumes UI actions; text entry reads text events.
Presentation consumes resolved actions and confirmed state.

Use an App-layer input service for physical-device state and bindings, because it must work before a session starts. Resolve menu/pause/text/gameplay context before World gameplay consumers run. Keep avatar command state in World-layer PlayerControl. Preserve the existing service phases and make input ordering explicit through their registration/dependency rules.

A small typed action frame can hold movement/aim axes, held states, and ordered press/release/cancel edges. Consume one-shot edges once per rendered frame; do not replay a press for every simulation tick caught up in that frame. Persistent commands continue until changed. Neutral stick readings must not cancel another device's movement unless arbitration transfers ownership.

Use one command-producing gameplay path for live devices. Existing high-level automation can keep its exact quantity/coordinate commands; route shared actions through the same helpers and add action-level tests so demos do not falsely imply the bindings are covered. Existing accepted-turn replay remains below this layer.

For analog movement, quantize before comparing/sending, bound magnitude, and coalesce continuous axis changes to a deliberate cadence. Preserve press/release order for attacks and thrust. Do not coalesce across a press or release edge. Update the joined-client preview whenever the authoritative movement contract changes.

Implementation sequence after an explicit implementation request

  1. Build the snapshot abstraction and synthetic source first. Extract action types and keyboard/mouse adapters; exercise binding, edge, context, and arbitration behavior without hardware.
  2. Add the semantic release command and test that accepted/rejected/delayed logistics jobs behave correctly. Move memory actions into Input and verify command/replay compatibility.
  3. Complete controller gameplay, nearby targeting, utility, choosers, and menu/pause navigation using timed synthetic scenarios, including a developer-only rendered replay path.
  4. Add the thin Windows native device reader and verify its backend/build integration. Keep directional walk/run and fixed bindings; analog speed and rebinding UI remain deferred.
  5. Validate discovery, mappings, reconnect, focus handling, and physical feel on an Xbox-compatible USB controller. Synthetic success does not establish physical integration.

Validation required during implementation

  • Bindings → actions: diagonal normalization, radial dead zone, stick-noise suppression, run, device takeover, and neutral input from an inactive device.
  • Context transitions: pause/focus/disconnect while walking, flying, aiming, or attacking; no stuck thrust or surprise attack when resuming. Verify the selected route/job cancellation policy.
  • Frame/tick boundary: one press produces one action at low/high frame rates and during multi-tick catch-up; continuous commands do not flood queues.
  • Feature parity: manual transfer cancellation across arrows/WASD/stick, pile target selection, memory controls, equip, jump/flight, and UI click consumption.
  • Determinism and presentation: record/replay exact accepted turns, host/client ownership, and joined-client preview convergence. Test analog speed if that contract changes.
  • Physical integration: connect/reconnect, more than one attached controller with one selected local device, focus loss, menu confirm/back, controller prompts, and browser parity if selected.

Existing tests cover keyboard Space flight/release, script-driven gameplay, replay equality, networking, and local/host/joined movement response. They provide a base but do not exercise a gamepad adapter or shared context arbitration. This review did not run Bazel tests because it changes documentation only.

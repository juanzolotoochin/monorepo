Networking · question from Juan

Why not gRPC for the game connection?

gRPC is mature, typed, and already used in this monorepo. It's a fair question why the game needs its own network layer. The short answer: gRPC would replace only the smallest part of it, and it handles packet loss in a way that hurts lockstep.

Short answer for Juan

Most of our network code is the lockstep protocol: turns, input delay, time sync, desync checks and joins. We'd need it on top of gRPC too. gRPC would only replace the bottom layer that moves bytes, and it does that over TCP. When one packet is lost, TCP holds back everything after it until the retransmit arrives, usually 150–300 ms later. In lockstep that freezes the game. Over UDP, the next packet 17 ms later already carries the lost data. On top of that, Steam and EOS relays are message-based, not TCP, so gRPC can't run over them without an adapter. gRPC is a good fit for services around the game: lobbies, accounts, uploading crash and desync reports.

Using gRPC wouldn't remove the protocol work, which is where the complexity is. The transport layer is also the one we must keep swappable, because Steam and EOS each bring their own.

The main technical reason

What happens when one packet is lost

The host sends one turn packet per tick, 60 a second. Packet 105 gets lost on the way to the client. Lockstep needs every turn, so the question is how fast the missing data arrives.

TCP (gRPC) guarantees order, so packets 106, 107 and later arrive but are held back by the operating system until 105 is retransmitted. That takes at least one round trip after the loss is noticed, and often a full retransmission timeout, around 200 ms or more. This is called head-of-line blocking.

UDP with redundancy, our design, has each packet repeat every turn the client hasn't acknowledged. Packet 106 carries turns 105 and 106, so the gap is filled 17 ms later, inside the input-delay buffer.

The usual practice in games matches this. The in-game connection is custom UDP or a platform transport built on UDP (Steam networking, EOS P2P, Unreal's NetDriver). Services around the game (matchmaking, accounts, stats, crash reports) use HTTP or gRPC.

Decision

How to build our UDP transport

There is a middle ground worth considering: QUIC, through the mature Rust library quinn. It runs over UDP and offers independent streams (one lost packet doesn't block the others), unreliable datagrams, encryption and connection handling.

Option A · recommended

Plain UDP, our own small framing

  • Lockstep redundancy means we barely need reliability code: acks plus repeating unacknowledged turns
  • Runs on the virtual clock in tests, and shares behavior with the Steam and EOS transports, which are also message-based
  • No async runtime
  • The save transfer and connection handshake are ours to write
  • No encryption, which Tailscale, Steam and EOS each provide anyway
Option B

QUIC via quinn

  • Reliable streams for the save transfer, datagrams for turns, encryption and handshakes, all off the shelf
  • Mature and well tested
  • Brings tokio; its timers are real-time, so it only works outside the loopback simulator
  • Only covers direct UDP; Steam and EOS still need their own transports
Option C

gRPC bidirectional streaming

  • Familiar, typed, mature
  • Head-of-line blocking stalls the game on every lost packet
  • Doesn't fit the Steam and EOS relays

Either way, gRPC still has a place in the project: a future lobby or matchmaking service, uploading desync dumps, and possibly the dev control protocol that scripts and tools use to drive the game.

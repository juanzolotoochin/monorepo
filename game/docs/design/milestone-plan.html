Lockstep milestone plan

Every architecture decision is now made. This page turns them into crates, an ordered roadmap and a determinism test plan for the monorepo's Bazel build. Three questions remain about order and verification.

Layout

Crates under game/

Each is a Bazel rust_library or rust_binary using rules_rs, like game/core today. The blue ones are deterministic and may never depend on Bevy, f32 math or wall-clock time. A Bazel visibility rule enforces that only view and app can see @crates//:bevy.

deterministicgame/fxFx type, vectors, trig and sqrt tables, decimal parsing
deterministicgame/simWorld tables, chunks, tick stages, queues, RNG, timers, hashing
deterministicgame/contentDefinition loading, sim/view split, name tables, rules hash
deterministicgame/saveSectioned format, remap on load, RON dump, diff tool
deterministicgame/netTurns, input delay, time sync, Transport and Sessions traits, loopback simulator, UDP
toolgame/headlessRuns save + input log, writes per-tick hashes, benchmarks
bevygame/viewRender extract consumer, interpolation, prediction, net graph
bevygame/appThe game binary: host, join, single-player

net is deterministic in the sense that its decisions only depend on its inputs and a clock it is given. That is what lets the loopback simulator run it on a virtual clock.

Verification

How determinism is tested

The headless runner takes a save and an input log and writes one hash per tick. Every determinism test is a comparison of two such hash files that should be identical.

Decision 1

Checking Windows against Linux

The monorepo's CI (BuildBuddy) runs bazel test //... on Linux only. Windows builds happen on developer machines. A determinism check needs both platforms to produce the same hashes, but they never run in the same place.

Golden hash fileschecked into game/testdata/
→
Linux CIevery push must match
→
Windows dev machinesame test, same files, must match

Goldens turn a two-platform comparison into two one-platform comparisons against the same file. Any machine that runs the test checks itself against every other platform. When a deliberate gameplay change alters hashes, a command regenerates the goldens, and the diff shows up in review.

Option A · recommended

Golden hashes, Linux CI, Windows locally

  • Works with today's CI unchanged
  • Any new platform (Steam Deck, a Mac) joins by just running the tests
  • A Windows-only break is only caught when someone on Windows runs the tests
Option B

Add a Windows CI runner now

  • Windows checked on every push
  • New CI infrastructure (a GitHub Actions Windows job or a self-hosted runner) and Bazel Windows caching to set up and maintain
  • Work spent on CI before there is a game
Option C

Golden hashes now, Windows runner at milestone 1

  • Option A while the core is small, then automated once gameplay code is landing every day
  • The same setup work, just later
Decision 2

When to upgrade Bevy

The monorepo has one Cargo.toml for every crate, pinned to bevy = "=0.18.1". The new view targets 0.20. Two Bevy versions in one build means renamed dependencies and two copies compiled. The old game has to keep working until the port reaches parity.

Option A · recommended

Upgrade first, as its own step

  • Old game moves to 0.20 in one focused change (0.18 → 0.19 → 0.20 migration guides)
  • The new view starts on the final version, and both games share one Bevy build
  • Doesn't block milestone 0: fx, sim, save and the harness don't touch Bevy
  • Migration work on code that will be deleted
Option B

Build the new view on 0.18, upgrade at parity

  • Nothing old to migrate
  • The new view is written against an old API, then migrated anyway
Option C

Two versions side by side

  • Each game on its own version
  • Two Bevy builds, longer compile times, confusing dependency names
Decision 3

View before network, or network before view

After the simulation core and harness, two steps remain in milestone 0: a minimal Bevy view and the netcode. Both are needed before you and your friend can play over Tailscale.

Option A · recommended

View first

  • Seeing the simulation (boxes on a plane, chunk overlay, sleep colors) makes every later bug easier to find
  • The net graph overlay needs somewhere to draw
  • The first network test with your friend is then something you can both watch
  • Netcode, the riskiest part, comes a step later
Option B

Network first

  • Risk first; it can be fully tested headless with the loopback simulator
  • Debugging by reading hash files and logs until the view exists
  • Your prototype already proved the netcode approach works, so its risk is lower

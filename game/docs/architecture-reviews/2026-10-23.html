Kestrel architecture

Where each piece of logic lives. The game is a deterministic simulation that every machine runs from the same inputs, with Bevy drawing it. Three rules decide where code goes:

Gameplay rules live in simFixed-point math, no Bevy, no floats, no clocks. Same inputs give the same bits on every machine.
Only commands go inKeys and clicks become a CommandKind. The network carries commands, never state.
The app only readsAfter each tick the app copies the settlement into mirrors and draws them, interpolated between the last two ticks.

2 · One frame

From a key press to the screen

What happens when you press F to dig, in order. Steps 1 and 6–7 are Bevy systems in app, chained in main.rs; steps 2–5 are deterministic.

1 · Inputapp

lockstep::keyboard_input, mouse_input, piles::input or a script through control call Game::dig(), which becomes CommandKind::DigDown.

2 · Sessionsession

Session::queue hands it to this machine's peer: a Host, a Client or a replay. lockstep::step calls Session::update(clock) every frame.

3 · Turnnet

The host puts the command in the turn for tick T (input delay ahead) and sends turns to clients. A client runs tick T only once it has turn T.

4 · Ticksim

World::step(turn) runs the six stages below, 60 times a second. The owner check drops commands for avatars you don't own.

5 · Hashsim · net

After housekeeping, step hashes the state. Clients report hashes, and the host compares them to catch a desync.

6 · Mirrorapp

After each tick lockstep::step keeps the last two settlements and the events in Game. mirror_settlement, piles::mirror and digging::update copy them into view state.

7 · Drawapp

Views place things between the two ticks by Game.alpha. Events (tosses, hits, layers dug) start effects, sounds and flying units. telemetry times the session, each tick stage and the copy for the FPS overlay (F3).

3 · One tick

The six stages of World::step

In sim/src/world.rs, which times each stage (World::stage_times). The world is split into chunks; two stages run in parallel per chunk and can only change the entity itself. Anything touching something else is a message, applied in a fixed order.

StageWhat it may doSettlement code it runs
1 · Apply commandsCommands in player order. A command for an avatar runs only for its owner. move_avatar attack dig pile_action transfer jetpack equip_weapon dispense memory_*all in settlement/mod.rs, delegating to avatar.rs, piles.rs, combat.rs
2 · Self update parallelEach entity changes only itself, reading last tick's world. settlement.self_updateavatars walk, fly and center on a dig; haulers move; threats advance
3 · Read phase parallelRead the world, write messages. No writes to state. settlement.readhauler decisions, projectile collisions, which threats a strike reaches, route planning (nav.rs)
4 · MergeConcatenate outboxes in a shuffled but seeded chunk order. generic, in world.rs
5 · Apply messagesOne queue per message type, applied in declaration order (messages.rs). economy resolve_docks reserve attach load unload pile_step strike projectile_* breach fireeconomy.rs, haulers.rs, piles.rs, combat.rs
6 · HousekeepingSingle-threaded bookkeeping and index rebuilds. The state hash follows. combat_housekeeping avatar_housekeeping dig_housekeeping pile_housekeeping memory_housekeepinga finished dig deepens the pit and drops ore into piles here
